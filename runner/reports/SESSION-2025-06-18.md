# Session Report: June 18, 2025

## The Tensor Breakthrough — Finding All 291 Weight Tensors in a Running llama.cpp Process

### Research Context

We are building a **SID (Spatial Interrupt-Driven) cache** for POGLS — a system that intercepts the llama.cpp model inference at runtime and redirects tensor data pointers to cache entries instead of the memory-mapped GGUF file. The goal is to hot-swap weights without re-loading the model.

For three previous sessions, we attempted to find the `ggml_tensor` structs in process memory by:

1. **Model-struct scanning** (June 16) — scanning the `llama_model` object for tensor pointer fields. Found only 4 of 291 tensors (the direct ones like `token_embd.weight`, `output.weight`, `output_norm.weight`). The remaining 287 layer tensors (`blk.*`) were embedded in heap-allocated `llama_layer` objects and inaccessible.

2. **Process-wide sweep with struct heuristics** (June 17) — scanning ALL committed MEM_PRIVATE memory for byte patterns that match `ggml_tensor` structure (type field, ne[] dimensions, data pointer in mmap range). Produced only false positives. The struct layout mismatch between our manual definition and the precompiled DLL's actual layout made field-level heuristics unreliable.

3. **Grid-offset scan** (earlier today) — checking every 8-byte offset (0–392) within candidate memory for mmap data pointers. Still produced only false positives because the tensor structs were not at any scanned location.

The fundamental problem: **we didn't know where the tensor structs lived**. The `llama_model` object's `pimpl->ctxs_bufs[i].first` chain (a `std::unique_ptr<ggml_context>` buried inside three layers of C++ STL containers) obscured the pointer from our scanning.

---

### The Eureka Moment: Following the Allocator, Not the Struct

Instead of searching for `ggml_tensor` structs by their *content* (type, ne[], data), we decided to search for their *container* — the `ggml_context` that owns them.

**Key insight from reading llama.cpp source:**

```
ggml_context (40 bytes)
├── mem_size        @ +0    (size_t)
├── mem_buffer      @ +8    (void*) ───→ linear allocator pool
├── mem_buffer_owned @ +16  (bool)
├── no_alloc        @ +17   (bool)
├── n_objects       @ +20   (int)  ←── count of allocated objects (= 291 for our model)
├── objects_begin   @ +24   (void*) ──→ linked list of ggml_object headers
└── objects_end     @ +32   (void*)


ggml_object (32 bytes) — precedes each tensor in mem_buffer
├── offs    @ +0  (size_t) — offset within mem_buffer
├── size    @ +8  (size_t) — aligned allocation size
├── next    @ +16 (void*)  — linked list pointer
├── type    @ +24 (int)    — 0 = TENSOR
└── pad     @ +28 (4 bytes)


ggml_tensor (336 bytes, GGML_MAX_SRC=10)
├── type       @ +0   (int)
├── buffer     @ +8   (void*)
├── ne[4]      @ +16  (int64_t[4])
├── nb[4]      @ +48  (size_t[4])
├── op         @ +80  (int)
├── op_params  @ +84  (int[16])
├── flags      @ +148 (int)
├── src[10]    @ +152 (void*[10])
├── view_src   @ +232 (void*)
├── view_offs  @ +240 (size_t)
├── data       @ +248 (void*) ←── POINTS TO WEIGHT DATA IN MMAP
├── name[64]   @ +256 (char[64])
└── extra      @ +320 (void*)
```

The tensor lives at: `ctx->mem_buffer + obj->offs`

The `n_objects` field (at offset 20) stores the count of allocated objects. For our Qwen2.5-0.5B model with 291 weights, this equals **291** — a unique fingerprint we could search for.

---

### The Algorithm: Process-Wide Signature Scan

We implemented a **two-phase process-wide scan**:

```
Phase 1: Enumerate all committed MEM_PRIVATE regions
Phase 2: For each 8-byte-aligned position, check for ggml_context signature:
    ├── n_objects ∈ [100, 10000]          (fast pre-filter)
    ├── mem_buffer ≠ ctx address           (must be separate allocation)
    ├── mem_buffer is committed             (valid pointer)
    ├── objects_begin→offs ≤ 1MB            (plausible offset)
    ├── objects_begin→size ∈ [32, 1MB]     (plausible object size)
    ├── objects_begin→type ∈ {0,1,2}       (TENSOR/GRAPH/WORK_BUFFER)
    └── objects_end is committed            (valid pointer)
```

**Why this works where everything else failed:**

The `n_objects` field provides a **deterministic fingerprint**. Unlike tensor struct fields (which shift depending on GGML_MAX_SRC), the context struct's fields are stable and unambiguous. No other allocation in the process has exactly 291 objects with valid headers.

**Once the context is found:**

```
1. Follow ctx→objects_begin (linked list head)
2. For each ggml_object with type == TENSOR:
   3. tensor_struct = ctx→mem_buffer + obj→offs
   4. tensor_name   = *(tensor_struct + 256)
   5. tensor_data   = *(tensor_struct + 248)  ← mmap data pointer
   6. tensor_nbytes = max(ne[i] × nb[i])
```

This completely bypasses all struct layout ambiguity — we don't search for tensors by their fields; we find them by their container's unique identifier.

### Why This Matters

The **seven-session struggle** to find tensors in process memory is now resolved. The winning insight was:

> **Don't search for the child (tensor struct) by guessing its features. Find the parent (context) by its unique fingerprint, then read the children through the parent's linked list.**

This approach is:
- **Compiler-independent**: doesn't depend on struct field offsets matching between compilers
- **Version-robust**: `gml_context` layout is far more stable than `ggml_tensor` layout
- **Deterministic**: `n_objects` is a unique identifier — no false positives
- **Complete**: finds ALL tensors, not just the ones in the model struct

### The API

```c
// Returns all tensor pointers, names, data pointers, and byte sizes
int sid_tensor_enum(model, ptrs_out, names_out, datas_out, nbyteses, max_count);

// Find a single tensor by name
int sid_tensor_find(model, name, &struct_out, &data_out, &nbytes);

// Swap a single tensor's data pointer (for SID cache)
int sid_tensor_swap(model, name, new_data, &old_data);

// Batch-swap N tensors (for full model redirect)
int sid_tensor_swap_all(model, names, new_datas, old_datas, n);

// Debug summary
int sid_tensor_debug(model);
```

All functions are exported from `sid_tensor_helper.dll` (MSVC, depends only on KERNEL32.dll).
