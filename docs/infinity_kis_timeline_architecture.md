# Infinity Kis Timeline — Full Cycle Cube Architecture
## Date: 2026-08-01

## The Architecture

### Core Concept
The Full Cycle Cube is NOT stored — it's TRAVERSED via the Infinity Kis Timeline, a cyclic process that alternates between dodecahedron and icosahedron geometries.

```
Infinity Kis Timeline:
  ... → dodeca(pos) → spike → icosa(neg) → spike → dodeca(pos) → ...
       [CPU routing]          [GPU batch]          [CPU routing]
```

### The Split: dodeca (pos) vs icosa (neg)

| Geometry | Sign | Role | Hardware |
|----------|------|------|----------|
| Dodecahedron | pos (+) | Routing, addressing, decisions | CPU |
| Icosahedron | neg (-) | Batch compute, parallel processing | GPU |

**Why this split?**
- Dodeca: 12 pentagonal faces → simple routing (which face, which position)
- Icosa: 20 triangular faces → easy GPU batching (triangles tile perfectly)

### World AB: 162/2, 162/3

The icosahedral address space (162 vertices) splits into:

```
162 = 2 × 81 (ternary) = 3 × 54 (binary)

AB split:
  A = 81 positions (ternary: 3⁴) — "where to go"
  B = 54 positions (binary: 2×3³) — "what to do"
```

**3⁴ = 81**: the TERNARY addressing — 4 levels × 3 choices each
**2×3³ = 54**: the BINARY addressing — 2 modes × 3³ traversal

### 27×6 Universal Traversal

```
27 = 3³ (three dimensions × three levels)
6  = faces of cube (6 directions: ±x, ±y, ±z)

27 × 6 = 162 = full icosahedral vertex set
```

**3³ traverses ALL dimensions**:
- Move in x, y, or z at each level
- 27 positions cover the entire 3D address space
- 6 directions ensure complete coverage

**This means**: from any starting point, you can reach ANY position in the geometry by following the 3³ traversal pattern.

### Address Space: 20736×20736

```
20736 = 144² = 12 × 12 × 144 = icosahedral face size
20736×20736 = face × timeline position
Timeline distance = 20736 (one full cycle)
```

**The cube is 20736×20736×∞** (infinite timeline):
- X-axis: face position (0..20735)
- Y-axis: timeline position (0..20735)
- Z-axis: depth (generated by spike conversions)

### How It Works

**Step 1: CPU Routes (dodeca pos)**
```
CPU: "I need weight at position (face, timeline, depth)"
  → Use 3³ traversal to find the route
  → Route through 27 positions × 6 directions
  → Arrive at icosa layer
```

**Step 2: GPU Batches (icosa neg)**
```
GPU: "I have 54 positions to compute"
  → Batch all 54 icosa vertices
  → Compute weight values using geometric operations
  → Return batch to CPU
```

**Step 3: Spike Conversion**
```
Spike: dodeca ↔ icosa conversion
  → Pentagons (dodeca) → Triangles (icosa) via spike operation
  → Preserves address space (162 vertices)
  → This is the "loop" in Infinity Kis Timeline
```

### Storage (What Gets Stored)

**Nothing is stored** — the cube is generated on-the-fly:
- Seed: initial position (few bytes)
- Codec: traversal rules (few bytes)
- Encoder: Kis Timeline traversal (built into hardware/software)

**The encoder IS the traversal**:
```
weight = encoder(coordinate, seed, codec)
       = traverse_kis_timeline(coordinate)
```

### CPU/GPU Split in Detail

**CPU (dodeca pos)**:
- Routing decisions (which face, which position)
- Traversal control (3³ pattern)
- Memory management (which batch to send)
- Latency-sensitive operations

**GPU (icosa neg)**:
- Batch computation (54 vertices at once)
- Parallel weight calculation
- Geometric operations (rotation, scaling)
- Throughput-sensitive operations

**The handoff**:
```
CPU: "Compute weights for these 54 positions"
GPU: [batch compute] → return 54 weight values
CPU: "Route to next 54 positions"
GPU: [batch compute] → ...
```

### Why This Works

1. **162 = 3³ × 6**: the icosahedral address space is perfectly structured for universal traversal
2. **dodeca/icosa split**: each geometry has a natural hardware assignment
3. **Spike conversion**: preserves address space while switching geometries
4. **Infinite timeline**: the process never ends — continuous computation

### Storage Implications

**Traditional approach**: store 568 MB of weights
**Infinity Kis approach**: store 0 bytes — generate on-the-fly

**The tradeoff**:
- Traditional: fast load, static weights
- Infinity Kis: no load, dynamic weights (generated by traversal)

**For inference**:
- CPU routes to weight position
- GPU computes weight value
- No memory bandwidth bottleneck (weights generated, not loaded)
